Project Overview

CV Generator is an agentic RAG system that turns a job description into a tailored, one-page résumé. Paste a JD and the agent retrieves your most relevant experiences and projects, lets you approve the selection, writes keyword-aligned bullets, fact-checks every claim against your real source material, and fills them into your Word template — then renders to PDF and guarantees it fits exactly one page. The entire workflow is orchestrated by a LangGraph stateful graph with a human-in-the-loop interrupt and automatic retry loops, and runs in a Jupyter notebook or interactively on LangGraph Studio.

How It Works: LangGraph Pipeline

The agent is a LangGraph StateGraph where each node is a specialized stage. After hybrid retrieval, the graph pauses on a human_review interrupt so you can approve or override the selection. The supervisor and render_check stages form two retry loops that send feedback back to the generator until every claim passes fact-checking and the résumé fits one page.

        ▼

The live graph in LangGraph Studio — __start__ → select → human_review → generate → supervisor → __end__, with render_check looping back until the PDF fits one page

Stage What it does
select Extracts technical keywords from the JD, then runs hybrid retrieval (dense embeddings + BM25, fused with Reciprocal Rank Fusion) over short per-item summary cards. An LLM picks the top ≤5 experiences and projects.
human_review A LangGraph interrupt pauses the graph so you can approve the selection or override it with your own picks.
generate An LLM writes only the bullet points. Titles, roles, and dates are hard-coded in a TITLES map, so names and dates are never hallucinated.
supervisor Programmatic checks (≤3 bullets/item, ≤300 chars/bullet) plus an LLM fact-checker that verifies every claim against the source README/report. On failure it sends feedback and regenerates.
render_check Fills the Word template, converts to PDF (MS Word via docx2pdf), counts pages, and enforces one page — if it overflows, it reports how many characters spilled over and regenerates shorter.

Retrieval Design

The retrieval architecture is deliberate — it separates what gets searched from what gets read, and separates facts from generated text. This is what keeps the résumé both relevant and truthful.

📄

One Project = One Document

Each README.md is a single retrieval unit — no mid-project chunking. A whole experience or project is retrieved or skipped as a coherent whole, never fragmented across unrelated pieces.

🔎

Retrieve on Short, Generate on Long

A keyword-dense summary card (cached) is embedded for retrieval; the full README/report is loaded only for the few selected items at generation time — fast search, rich context only where it counts.

✅

Titles are Facts, Bullets are AI

Headings come from a hand-maintained TITLES map; the model only writes bullets. This eliminates renamed companies, invented dates, and dropped items — the most common résumé-LLM failure modes.

🔀

Hybrid Retrieval with RRF

Dense semantic search (HuggingFace multilingual MiniLM embeddings + Chroma) and sparse keyword search (rank_bm25) run together, fused with Reciprocal Rank Fusion — catching both meaning-based and exact-keyword matches from the JD.

⏸️

Human-in-the-Loop Interrupt

A native LangGraph interrupt pauses the graph at human_review. Resume with an empty command to accept the AI's selection, or a list of names to override it — you stay in control of what lands on the page.

📐

Guaranteed One Page

render_check fills the template, renders to PDF, counts pages with pypdf, and loops back to shorten if it overflows — reporting exactly how many characters spilled over so the next pass trims precisely.

AI Model & Retrieval Stack

Models are matched to each task: a fast, cheap Claude Haiku handles high-volume keyword extraction, selection, and summary cards, while a stronger Claude Sonnet handles generation and fact-checking where quality matters most.

Component Model / Tool Role
Keyword / Selection / Summaries Claude Haiku Fast, cheap, high-volume tasks
Generation / Fact-Checking Claude Sonnet High-quality bullets + verification
Dense Retrieval paraphrase-multilingual-MiniLM-L12-v2 + Chroma Semantic embedding search
Sparse Retrieval rank_bm25 + Reciprocal Rank Fusion Exact keyword match, fused with dense
Document I/O python-docx · docx2pdf · pypdf Fill template → PDF → page count
Orchestration / Observability LangGraph + LangSmith Stateful graph, HITL, traced runs

Technical Implementation

1. Hybrid Selection

  • An LLM extracts technical keywords from the raw JD before retrieval, so the query is normalized to skills rather than prose
  • Dense (Chroma) and sparse (BM25) rankings are merged with Reciprocal Rank Fusion, then an LLM picks the top ≤5 items
  • Retrieval runs over cached summary cards (summaries.json) — keyword-dense one-liners that keep similarity focused and search fast

2. Fact-Checked Generation

  • The generator writes only bullets; display titles and roles come from a TITLES dict (name → (display_title, role)) so they are never hallucinated
  • Supervisor enforces hard limits (≤3 bullets/item, ≤300 chars/bullet) and runs an LLM fact-checker against the full source README/report
  • On any failure, structured feedback is fed back to the generate node, which regenerates up to MAX_ATTEMPTS times

3. Template Filling & One-Page Enforcement

  • The filler locates the EXPERIENCE and SKILLS headings in the .docx and replaces everything between them, cloning the template's paragraph formatting
  • Header, Education, and Skills sections are left completely untouched — only EXPERIENCE and PROJECT bullets are rewritten
  • render_check converts to PDF via docx2pdf (local MS Word), counts pages with pypdf, and loops back to shorten until it fits one page

4. Configurable Knobs

  • MAX_PICK, MAX_BULLETS, MAX_BULLET_CHARS, MAX_ATTEMPTS control how many items appear and the page budget
  • Swap in any .docx template; the model assignment (Haiku vs Sonnet) is configurable per node
  • agent.py is exported from project.ipynb so the same graph runs in a notebook or via langgraph dev on LangGraph Studio
